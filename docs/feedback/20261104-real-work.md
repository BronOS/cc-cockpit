## Problem
The problem right now is that the result does not correspond my workflow (i think anybody's workflow). How does my workflow looks like:
1. check chat - this is top priority and required must operative answers and actions
2. check email - this is second priority after chat, but also usually required operative reaction
3. jira tasks - this is latest job items stream

The ordering of actions what are required my attention is totally wrong right now and even more - the whole system looks like non-deterministic/unpredictable, because of number/amount of manipulations was applied to each incoming job items - jev triage, re-grouping, etc... This feeling become from the major mistake what i made in the design of this system - triage. The main daily drive suppose to be an Inbox panel where i need sorted items by my own rules from different sources (jira, email, chat, calendar), but now i either see wrong sorting or needed items are not in the list. The mistake was made by me in 2 places:
1. the word "triage" is incorrect, the meaning is a sorting or priority
2. the place where it was applied - in both places: first, is in source, like jira or email and second in the Inbox, what made the result unpredictable. The source has to be a source (data provider) nothing more and i mixed up everything - the view, controller and jev triage. The plugin by itself can do of this things if it needs to, but for Inbox feed it has to be just a data provider without anything on top. For example, jira. It can re-group items by status, sort/order, apply jev triage and do anything it needs to build own view for the user, but when it become to data-provider (inbox-feed data provider) it has to register only one interface to fetch the data (following defined interface, this part needs to be carefully defined, in other words the interface definition has to cover all cases, at least all know for this moment cases)

## Inbox Solution
The main idea is a decoupling of - how data should be fetched and how data should be shown and by whom. The data provider is a plugin, such as gmail or jira. The Inbox is a consumer what is passively listening events for new items. The plugin fetching data from own source and when new items are dropped, it broadcasting event. Who needs it, listening and Inbox one of them. Once item become to the Inbox, it can apply own rules to sort, triage, etc... and display it.

Now the question (this part is not finished and highly discussable) - what can be done with items and how to show it? Let's say one item can be opened in overlay another, like calendar, can not. One item can be marked as read another not. One item become to the union list sorted/filtered by internal rules another not. In one hand it looks like the item belong to the data source/plugin and only it can know how to properly display it in Inbox (is it part of union list or draw as a calendar), in other, Items can be unified and Inbox will have a control on it if it needs it. As an alternative (it is not a decision yet, still required discussion and might be even totally different solution) this could be bundled plugin or/and provide API to draw calendar part, item part and so on and a plugin can register own function for each.

## Decisions (discussion)
1. A source is only a data provider: all items, facts only, no level, no dropping, no grouping. "Triage" becomes priority/sorting.
2. The Inbox orders by the person's rules, in their order, first match wins; deterministic. Default: by source (Chat, Email, Jira), then rules within.
3. Jev stays, as one kind of rule condition (e.g. "Jev: urgent >= 0.8"), answer cached per item so the order is stable. It is how a lower-priority source wins a top place (the boss email).
4. The Inbox knows no source. A source emits an "item" event with the data by contract, including the item's actions. The Inbox draws a standard row and routes a clicked action back to the source (`source.act(id, action)`); the source opens its own overlay, marks read, etc.
5. Non-row content (calendar, later others) goes into slots: the app gives panels a slot API, the plugin draws its own page in the slot, the Inbox only places it. Plugin code never runs inside another plugin's page.
6. Item event fields (draft, accepted): id, source; title, preview; time (sort key); from {name, address};
   to (direct / group / cc); mentionsMe; read (null = n/a); place (channel / folder / project+status);
   labels (free tags, e.g. "assigned", "priority:high"); actions [{id, label}] (open, markRead, markUnread, done).
   Rules can match any field; Jev reads title + preview.
7. Item lifecycle: `item` (new or changed, whole item, rules re-run), `gone` (no longer the person's business:
   archived, closed, resolved; removed), `sync` (the source's full current list at start and after reconnect, repairs
   missed events). The Inbox's own Done/Hide is Inbox memory by item id, hides until a newer `item` event, never
   touches the source.
8. Rules: ordered list, first match wins, puts the item in a named group (e.g. Now / Soon / Later / Rest, order set
   by the person); newest first within a group. A rule is one or more field conditions (all must hold) or one Jev
   question with a threshold. Each row shows the rule that placed it ("rule 3: Jev 0.86"). Edited in the Inbox's
   settings (the central settings place).
9. Slots (app feature): a panel places a named slot type ("agenda here, 200px, above the list"); a plugin declares in
   plugin.json that it fills that slot type; the app embeds that plugin's own page there, isolated like a panel; the
   project picks the provider when several exist; no provider = no slot. Any plugin can define new slot types.
10. Overlay: kinds stay html (any drawing, the plugin's own page) / terminal (a real command in a PTY) / url (a foreign
    site). New: the toolbar is the app's. The opener tags the overlay with a type + data (`inbox-item {source, id}`,
    `file {path, mime}`) and its own buttons (Mark read); other plugins register buttons per type (Editor "Edit" for text
    files, Jev "Improve triage" for inbox-item, core "Discuss with Claude" for all). A click runs in the button
    plugin's own host with the type + data, never the other page. The app opens the overlay at once with a loader until
    the page is ready (fixes 8). Discuss with Claude: note optional, switches to the new tab (fixes 9, 10).
11. Sessions as a bundled plugin: builds on existing ctx.sessions.list() + onChange. Missing in the app: all-windows
    scope, actions (focus incl. window switch, close, rename), and the top-bar strip + Sessions panel become slot types
    (`sessions-strip`) filled by the bundled plugin, replaceable. A plugin sees status and title only, never terminal
    content, and cannot type into a session.
12. Settings: one Settings window: General, Appearance, Keybindings (own page), Plugins (installed + marketplace
    merged; per plugin a gear to its global settings), This Project (per plugin: each field "use global" or override).
    A panel's header gear opens the project page when the plugin has project settings, else the global one. No
    settings forms inside panels (guide + review rule). A plugin may supply its own settings page (html) shown inside
    the central place, for rules editors that do not fit a form.
13. Style guide: the app injects a component stylesheet into every plugin page (native-looking button, input, select,
    .cc-card, .cc-list, .cc-row...), plus a `ccc guide style` topic with the components and rules (spacing, sizes, when
    to use what). Review checks plugin pages, html settings pages included, follow it; own controls only where the
    components don't fit.
14. Marketplace: preview image required (`preview.png` in the repo at the pinned tag, size-capped; the index check
    refuses a listing without one, existing listings get a grace period with a warning); "Update all" on the Plugins
    page (same checked install per plugin, failures listed after); the whole index fetched, shown ~20 per page with
    search and category/installed filters.
15. Roles: Inbox = "what needs me now" (the person's rules across sources; needs a source). Source plugin = "everything
    from here" in its own structure (Jira by project/status, Chat by space, Gmail by label, Calendar by week), may use
    its own Jev for its own view, works without the Inbox. Same item = same actions everywhere (from the source). The
    Inbox hides nothing for good: unplaced items in a collapsed "Rest" group, a Done view, search. Each source states
    its scope ("unread + last 14 days", "my open tickets") in panel and settings. Optional: the source panel marks
    items that are in the Inbox ("Now").
