# Downloads to the person's device

External review:

## Overview
- Get a file or a folder from the cockpit machine onto the device the person is at (design `docs/design-download.md`
  revision 3, the source of truth): a browser view, server mode's browsers and the desktop's remote window.
- Two ways in: the Files panel's right-click menu (cockpit.files 0.4.0: Download, Download as .zip, Download as .zip with
  .git and node_modules; the click is the gesture, no confirm) and `ccc download <path>` (Claude offers; an armed
  `ApprovalDialog` in every browser view of the window, first accept wins).
- A file downloads as itself; a folder as a `.zip` streamed by our own writer on `node:zlib`, capped at 2 GiB of file
  bytes and 20,000 entries, `.git` and `node_modules` left out unless the person includes them.
- Transport: one-use, per-view, cookie-bound tokens on a gateway route `GET /d/<token>`; the remote window saves straight
  to the desktop's Downloads under its own gates (origin, a fresh click, one at a time, a budget, 4 GiB, a sanitised name).
- The local desktop page has no Download (the file is already there).

## Development Approach
- **testing approach**: Regular (code first, then tests); every task ends with its tests, all passing before the next.
- main is the authority: the view comes from the connection or HostApi's `originOf`, never the payload; every path is
  re-resolved and re-checked at the GET; the remote window's gates are the desktop's, never the page's.
- No Electron in `main/files/downloads.ts`, `zip-writer.ts`, `folder-walk.ts`; `will-download` and `app.getPath` stay in
  `electron-remote-window.ts` (logic in `remote-windows.ts`), `showItemInFolder` through `electron-shell.ts`, no `dialog`.

## Solution Overview
- `main/files/downloads.ts` owns starts, offers, tokens and live streams; the gateway only routes `/d/` to it and tells it
  about revokes, disconnects, None exit and stop.
- A Files click: origin view → path and caps checked → a token for that view → `downloads.start` to it alone → the shell
  clicks a same-origin `<a download>` (or shows "ready — Download" when it lost activation).
- `ccc download`: an offer through `SharedAsks` to every browser view (held in server mode) → Download posts
  `downloads.accept` on the view's socket → main re-walks and takes the Files path for that view.
- The remote window turns `will-download` from cancel-all into a checked save to a hidden temp name, linked exclusively to
  the final name on completion.

## Technical Details
- `src/shared/downloads.ts`: `DOWNLOAD_ZIP_MAX_BYTES` 2 GiB, `DOWNLOAD_ZIP_MAX_ENTRIES` 20,000, `DOWNLOAD_TOKEN_MS` 60 s,
  `DOWNLOAD_OFFER_MS` 10 min, `DOWNLOAD_CLICK_MS` 5 s, `DESKTOP_DOWNLOAD_MAX_BYTES` 4 GiB, walk depth 64 and 10 s; payloads
  `downloads.start {requestId, url, name}`, `downloads.offer {requestId, path, real?, kind, outside, size | counts,
  skipped, runnable}`, `downloads.failed {requestId, reason}`, `downloads.settled {requestId}`; `downloadName` (gateway),
  `contentDisposition`, `desktopSaveName` (remote window).
- Token: 32 random bytes base64url, in memory, bound to `{ deviceId, viewId, windowId, path, kind, includeAll }`,
  consumed when the 200 headers go out; a refusal is 204 with no body plus `downloads.failed` to the token's view.
- Limits: `ctx.files.download` 10 per 60 s per plugin; offers 3 waiting and 10 per 10 min per window; streams 2 per
  device, 3 zips app-wide; remote window one active per server, 3 per 10 s per server.
- Zip entry: bit 3 and bit 11, method 8 (`createDeflateRaw` level 6), CRC by `zlib.crc32` per chunk; folder entries
  stored; made by Unix, `0644` / `0755` only; DOS time in local time plus `0x5455` UTC.
